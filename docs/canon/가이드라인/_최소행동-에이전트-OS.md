# ⚙️ Minimum Action Agent OS — 적용 규약

> 이 문서는 **작업 방법론**이다. 무엇을 쓸지(내용)는 캐논이 정하고, 이 문서는 **한 번에 몇 개의 선택지를 볼지**만 정한다.

## §0 단 하나의 규칙

**어떤 reasoning node도 한 번에 직접 선택할 수 있는 액션(Agent · Tool · Skill · MCP · 기타 callable)이 5개를 넘지 않는다.**

넘을 때만, 아래 순서로 **최소 수정**한다:
1. 불필요한 Tool 제거 → 2. Skill로 묶기 → 3. 역할 분리 → 4. Router 계층화

이미 5 이하인 노드는 **그대로 둔다.** 구조를 위해 구조를 바꾸지 않는다.

> [!warning] 강제 수단 부재 — 가짜 청결 금지
> `.claude/settings.json`에는 permissions 블록이 없고, 이 규약을 **기계적으로 강제하는 장치는 존재하지 않는다.** 본 규약은 **PM이 편성 프롬프트에 계약으로 써넣을 때만** 효력을 갖는다.
> 따라서 §7에 "달성"을 적을 때는 명목 액션 수가 줄었다는 뜻이 아니라, **그 배치의 프롬프트에 계약이 실제로 들어갔다는 뜻**으로만 적는다. 강제 없이 "PM ≤5 달성"을 선언하면 CLAUDE.md §3 D2(어휘 카운트만 보고 청결 선언)와 동형의 **가짜 청결**이 된다.

## §1 이 프로젝트의 노드 지도

이 저장소에는 `.claude/agents/`·`.claude/skills/`·`.claude/commands/`가 **모두 없다**(3건 실측 부존재). 에이전트는 파일로 정의되지 않고 **PM이 런타임에 프롬프트로 편성**한다. 따라서 Local Action Space는 파일 개수가 아니라 **각 노드에게 실제로 열려 있는 선택지**로 센다.

| 노드 | 역할 | 계층 |
|---|---|---|
| **PM (메인 세션)** | 작가 입력 → 작업 유형 판별 → 편성 | Router |
| 뼈대·설계관 | 자산·캐논 → 화별 뼈대 / 설계 시안 | Worker |
| 집필관 | 뼈대 1화 → 원고 1편 | Worker |
| 점검관(산문·논리·낭독) | 원고 1편 → 발견 목록 **파일** | Worker |
| 수선관 | 발견 목록 → 원고 수술 | Worker |
| 검증관·재검관 | 산출물 → 정합 판정 | Critic |
| 등재관 | 신규 요소 → 캐논 동시등재 | Worker |
| 인계표 작성관 | 뼈대+직전 화 실측 → 화 경계 표(프롬프트 주입물) | Worker |

## §2 PM Router — 작업 유형 5개

**「대화」는 라우팅 유형이 아니라 기본 상태(non-routing default)다.** 작가 입력이 아래 5유형 중 하나로 **명확히 판별될 때만** 편성을 연다. 판별되지 않으면 PM이 직접 답한다 — **모든 입력이 배치를 부르지 않는다.**

| # | 유형 | 진입 조건 | 편성 |
|---|---|---|---|
| 1 | **뼈대·설계** | 구조·수순·시안 결정, 아크 설계 | 자산조사관 N → 뼈대관 1 → 정합 검증관 1 |
| 2 | **집필** | 뼈대 **승인 후** "N화 써줘" | 인계표관 1 → 집필관 N → 검증관 1 + 등재관 1 |
| 3 | **점검** | "점검·검토·읽어봐" | 산문·논리·낭독 3관 |
| 4 | **수선** | 점검 결과·작가 리뷰 존재 | 수선관 N (자기 반박 의무) → 재검관 1 |
| 5 | **정본화·스윕** | 규범 승격·캐논 등재 단독·기계 전수 치환 | 등재관 1 또는 **에이전트 0**(기계 스윕 — 점검-체계-정본 §2) |

**혼합 배치 허용.** 실적상 한 배치가 두 유형을 겹치는 일이 상시다(수선+점검 동시 등). 그때는 **각 유형의 편성을 병렬로 열되, 노드별 액션 수 제약은 개별로 지킨다.** 단일 분류를 강제하지 않는다.

> **1번이 2번보다 앞선다.** CLAUDE.md §2 「뼈대 우선 — 산문은 전 층위 뼈대 승인 후에만」이 최상위다. 뼈대 미승인 상태의 집필 요청은 1번으로 라우팅한다.

## §3 Worker 노드 — 역할별 도구 화이트리스트

각 Worker에게 **아래 목록 외의 도구를 쓰지 않는다는 계약**을 프롬프트에 명시한다.

| 노드 | 허용 액션 (≤5) | 편집 권한 |
|---|---|---|
| 뼈대·설계관 | Read · Grep · Bash · Write **(4)** | 뼈대 문서만 |
| 집필관 | Read · Grep · Bash(게이트) · Write · Edit **(5)** | 담당 화 파일만 |
| 점검관 | Read · Grep · Bash(카운트) · Write **(4)** | **`_점검/*.md` 신규 생성 전용** — 원고·캐논 편집 금지 |
| 수선관 | Read · Grep · Bash(치환·게이트) · Edit **(4)** | 담당 화 파일만 |
| 검증관 | Read · Grep · Bash(게이트 실행 포함) · Write **(4)** | 보고서 파일만 — 원고·캐논 편집 금지 |
| 등재관 | Read · Grep · Bash(validate_canon) · Edit **(4)** | 캐논 문서만 |
| 인계표관 | Read · Grep **(2)** | 없음 — 산출물이 프롬프트 주입물이라 파일 불요 |

**설계 근거(Critic 실증)**: 점검관의 정본 산출물은 `원고/…/_점검/00N화-점검.md` **파일**이다(커밋 `4a87ec64`·`78e335b6`에서 6건 생성 확인). Write를 빼면 그 배치가 실행 불능이 된다. 집필관은 프론트매터 「수술 이력」 append와 기존 화 수선을 수행하므로 **Edit이 필수**다 — Write 전용은 점검-체계-정본 §3-5 「원문 보존·append-only 우선」과 충돌한다.

**검증 가능성도 화이트리스트 설계 기준이다.** 안전만 보고 자르면 노드가 자기 임무를 완수하지 못한다(Critic 자신이 python 부재로 게이트 실측을 못 한 사례).

## §6 감사 절차

새 노드를 추가하거나 편성을 바꿀 때 **그 노드의 액션 수만** 센다. 5 초과 시 §0 순서로 최소 수정하고 결과를 §7에 기록한다.

**협약 6항과의 관계**: §7은 *액션 수 변동*의 기록처이고, **이탈의 원인·패턴 기록은 CLAUDE.md §3 이탈 로그가 정본이다.** 이 문서가 협약 6항을 대체하지 않는다 — 방법론 이탈이 발생하면 §7에 1줄, **근본 원인은 CLAUDE.md §3에** 적는다.
